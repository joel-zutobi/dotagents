# UI iteration

Use within Light for approved presentation work. Read the project's design
brief and platform instructions; keep the main workflow's authority boundaries.

1. Pin the approved prototype commit or images and affected screens/states.
   Compare equivalent viewport/device size, appearance, and data. Reuse existing
   components and behavior; make a new mockup only to resolve a design question.
2. Batch a connected flow with the same coder through corrections. Finish
   related layout, copy, and component changes before a coherent build/check
   run. Give shared components one writer and inspect affected consumers.
3. Plan an initial check run that supports several changed screens and their
   interactions. Use the platform's browser, simulator, device, or preview tools.
   Plan a separate release artifact only when needed and authorized. Reuse
   compatible builds and installed apps; build counts remain estimates.
4. Inspect settled screens against the reference: spacing, typography, grouping,
   panel treatment, and action hierarchy. Exercise changed navigation/editing
   and affected empty, selected, loading, and error states. Cover supported
   appearances affected by the change and respect actual owner deferrals.
5. Verify behavior proportionally. Saving, deletion, selection, playback,
   permissions, and persistence need relevant functional checks. Spacing and
   decorative colors need visual evidence rather than tests of padding values.
   Escalate changed high-impact behavior, not merely the styling of its screen.
6. Return the candidate, comparison captures, checks, and unresolved differences.
   The orchestrator accepts fidelity and returns corrections to the same coder.
   Use the selected review shape; this profile adds no automatic waiver.
7. Retain evidence with its source commit and reference. Documentation or
   handoffs alone do not invalidate it. Recheck affected integration changes
   and preserve separate release and distribution evidence where applicable.
